# Map of Time（时间地图）

[![Build](https://github.com/Geno1024-AIGC/map-of-time/actions/workflows/build.yml/badge.svg?branch=master)](https://github.com/Geno1024-AIGC/map-of-time/actions/workflows/build.yml)

记录一次出行被切成的许多小段——现实中的一条路、两个交叉路口之间——并靠多次经过累积出每一段的**典型耗时**。

步行、自行车、电驴、驾车四种方式分别统计：同一条路，走路、骑车、骑电驴和开车的时间没有可比性。

## 两种应用模式

设置页的「应用模式」可在**经典**与**聚合**之间切换，切换后整个界面（含配色和导航）立刻换成另一套布局，共用同一份行程数据：

- **经典**：原来的录制、切段、路网、命名、统计与设置全部保留，数据模型不变。
- **聚合**：只读。点不来自任何切段：它把全部已完成行程的原始 GPS 定点按空间密度聚出来（`agg/AggNetwork.kt`，30 m 网格 + 邻域合并，至少 6 个定点才算一个点），再把连续轨迹落在两个点之间的那一段记成一次经过，按出行方式聚合典型耗时。点身份只在本次重算内有效，不写库、不迁移旧 edge/leg/sample，因此不会破坏经典模式的历史统计。切换到聚合模式时从数据库重算；新数据进来后下次刷新即更新。

聚合模式只有一个简化的地图 / 地点 / 行程三页外壳，不提供录制、手动切点、命名与编辑——这些仍属于经典模式。路网页默认把最近经过的原始 GPS 路径叠加成「走过的路」路网，也可切回「点位连线」的直线概览；点线条或卡片可下钻到只读历史：一条连接会列出每次经过的日期、方向、耗时与实际 GPS 路径（典型/最快/最慢由这些记录算出），一个地点会列出连接与到访时间，一次行程会显示原始轨迹和它产生的经过。点击经过还能跳回对应行程。

## 下载

每次推送到 `master`，CI 会跑测试与 lint、用组织密钥签名，并把 APK 发布成一个滚动的预发布版本：

<https://github.com/Geno1024-AIGC/map-of-time/releases/tag/canary>

`canary` 标签始终指向最新一次成功的构建，旧包会被同名替换；签名一致，可以直接覆盖安装。版本号、构建序号和对应 commit 都写在发布说明里，便于回溯。

应用内也能更新：设置页的「应用更新」卡片会读取同一个发布，发现更新的 commit 就能一键下载并交给系统安装器。

## 应用内更新

- 只读 `https://api.github.com/repos/Geno1024-AIGC/map-of-time/releases/tags/canary` 一个接口，无需令牌。**元数据永远来自 GitHub**；镜像只用于 APK 文件传输。应用启动时静默检查一次，6 小时内不重复；设置页可以手动重查。
- APK 下载源可在设置页选：直连 GitHub、`ghfast.top`、`gh-proxy.com`、`ghproxy.net`，也可填任意自定义前缀。先试选中的源，失败再依次尝试其余预置源，单个域名失效不会卡住更新。
- 版本比较只用 `env`（commit 数），它同时就是 `versionCode`，所以「有没有新版本」与 Android 安装时的判定永远一致；同一个 commit 的 `pack` 变大不算更新。已安装版本从 `PackageManager` 读取；若版本戳无法解析，明确报「无法读取已安装版本」，不会退化成「已是最新」。
- APK 下载到 `cacheDir/updates/`：先写 `.part`，总长度与 ZIP 头（`PK`）都通过后才原子改名为成品，中断的下载永远不会被当成可安装的包。安装走 FileProvider 的 `ACTION_VIEW`，OEM 上回退 `ACTION_INSTALL_PACKAGE`。Android 自己会拒绝任何不是同一个签名密钥的包。
- 首次安装需要授予「安装未知应用」权限：应用会跳到本应用的授权页，回来后再次点「安装」即可。
- 发现更新时，底部「设置」标签上会出现一个小圆点，下拉到设置页即可看到版本说明。

## 它想回答的问题

> 从家走到地铁站，到底要多久？下雨天、早高峰、拎着东西的时候，又分别是多久？

一次出行只能给一个样本，而一次样本会被红灯、接电话、找路污染。所以这个应用把行程切成可重复识别的小段，每走一次就为沿途每一段各留一个样本，再用稳健统计给出「典型值」和「可信程度」。

## 两层切分：几何与路网

这是设计的核心，也是「按转弯停顿切」与「按 OSM 路网匹配」两种思路的折中。

### 第一层：纯几何切分（永远可用，完全离线）

`core/Segmentation.kt` 把原始 GPS 轨迹变成 **leg（行程片段）**：

- **清洗**：丢弃精度过差的点、时间倒流的点、超出该模式物理速度的跳变。
- **跳变即断点**：瞬移不是移动。轨迹在新位置继续，但两侧绝不会被连成一段。
- **长停顿断开行程**：超过该模式阈值（步行 90 s、自行车 / 电驴 120 s、驾车 150 s）的静止属于「休息」，两侧各自成段，等待时间不计入任何一段。
- **短停顿留在段内**：等一个红灯是这条路成本的一部分，不能从样本里剔掉；它会在段内被单独记为「等待」（见下）。
- **转弯切段**：以当前片段的起始航向为基准，方向变化超过该模式阈值（步行 65°、自行车 / 电驴 55°、驾车 50°）即认为进入另一条路。基准每 120 m 重新取一次，长弧线的弯道仍算同一条路；圆角路口、斜穿路口、在路口等灯后再转都能切开（若要求「单点前后 8 m 内转完 65°」，这几种都会漏切）。切点取区间内弯曲最大的点，尽量落在路口上。
- **手动切段**：录制时点「在此切段」，在算法没识别出的路口补一刀。
- **过短片段吸收**：不足最小长度/时长的碎片并入相邻段，绝不跨过停顿。

这一层不依赖任何网络或地图数据，飞机上、地下通道里都能工作。

### 第二层：按 OSM 交叉口再切（有数据时）

`osm/RoadGraph.kt` + `osm/JunctionSplitter.kt`：

- 把 leg 经过的每个**真实交叉路口**再切开。路口的定义是 OSM 中**度数 ≥ 3 的节点**——三条及以上道路在此相接。只是因为一条路被拆成两个 way 而出现的度数 2 节点，不算路口。
- **路口按出行方式区分**（`osm/RoadAccess.kt`）：走路时 `footway` / `path` / `pedestrian` / `steps` / `sidewalk` / `crossing` 都算路口的臂——人要过街；开车 / 骑车时这些臂不算，路中间的斑马线因此不再把车行段切一刀，车行段的端点落在真正的相邻路口上。`cycleway` 刻意留在车行一侧给骑车用。点位身份仍共用（`osm:` / `geo:`），只是切段用的路口集合随模式变：`RoadGraph` 为两种 traveler 各建一套路口，`JunctionSplitter.split` 按 `trip.mode` 选。点的自动副标题也只取同模式边的路名，不会让车行点挂上步道名。**切段规则变了，已有 edge key 会变，需要「全部重算」**；`insertEdge` 只补空、不重写已有 key，老数据不会自动迁移。
- 路口必须被**真正经过**：轨迹要靠近到 22 m 以内，并且是局部最近点。平行街道上的路口距离恒定，不构成局部最小值，因此不会把沿街的直行误切成一堆碎片。
- 12 m 以内的重复命中合并，8 m 以下的碎片并入相邻片段，保证每段的时间和距离都不丢。
- 路网按约 0.02°（≈2 km）的瓦片缓存，一次分析最多取 16 个瓦片。**任一瓦片失败就停止本次请求**：公共 Overpass 忙的时候单个瓦片要等几十秒，逐个重试只会让人以为应用卡死。
- Overpass 把超时或内存不足报成 HTTP 200 + `remark`。这种回答按失败处理，绝不写进缓存——否则这块区域会被记成「没有路」，直到缓存过期。
- 分析结束会注明 OSM 的状态：已匹配 / 未开启匹配 / 无路网数据 / 请求失败 / 范围过大，而不是只给一个 `OSM: 0`。

最终单位是「两个交叉路口之间的一小段路」，与这次走了多长、从哪里出发无关。

### 没有路网数据时

退化到**本地拐点聚类**（`geo_nodes` 表）：把行程端点吸附到 25 m 内曾经出现过的拐点，重复走同一条路就能累积到同一个身份上。功能完整，只是身份没有 OSM 路口那么稳定。

## 边身份（edge key）

| 前缀 | 含义 | 是否默认计入统计 |
|---|---|---|
| `osm:<a>-<b>` | 两端都是 OSM 交叉口 | 是 |
| `geo:<a>-<b>` | 两端都是本地聚类拐点（离线回退） | 是 |
| `mix:<a>-<b>` | 一端是 OSM 交叉口、另一端在路中间 | 否（`partial`） |

- 端点对是**排序后**的，所以往返走同一条街会落在同一个边上；方向作为每个样本的属性单独记录。
- `osm:` / `geo:` / `mix:` 三个命名空间互不相通，同一个数字 id 不会让不同类型的端点撞在一起。
- 行程的起点和终点通常落在路中间，因此首尾片段是 `partial`：它们仍然会被记录、在地图上能看到，但默认不参与「典型耗时」，避免把半条街的时间混进整段。
- 设置页可以打开「包含不完整片段」，把这个选择权交给用户。
- 边只按**两端原子点名**命名，优先级：两端点名拼出的「A × B」、OSM 的 `name`、key。点在命名时若填了含「×」的文本（例如「科创路 × 学府路」），那被当成**路名列表**存到 `node_roads`/`roads`，不会成为点名，更不会拼进边名——这正是旧的「万科翡丽山5号门 × 科创路 × 学府路」三段式名的根因。给边填的 `user_name`（路名）是**推断素材**，不再覆盖边显示名。两个端点是一级 `Node`（`osm:<节点 id>` 或 `geo:<聚类 id>`），命名一个点或一个路口都会同时改掉所有经过它的边；重新分析只刷新 OSM 名字。把点名清空就退回下一层。
- **路名挂在点上，交叉点由路名列表拼出来**：命名点时把它们所在的路（可多选）确认下来，几条路相交那个点就显示「科创路 × 学府路」。命名对话框把**相邻边已有的路名**和**附近点已选的路名**列为候选芯片，只是建议、不自动写入；你点选并保存才算数。一条路会被路口切成很多边，给边起的路名在命名其它点时也能一键复用。离线没有道路拓扑，所以不做「按几何自动连成整条路」：那会把同一条路的 GPS 抖动当转弯切断，又把岔路误当成同一条。名字的一致性交给你点选，不交给猜测。
- 两端同名、或任一端名字里带「×」时都不拼「A × B」：前者是路口内部的 20–40 m 连接段（「X × X」什么也没说），后者是路名交叉而非点名，两种都退回 OSM 路名或 key。组合名（交叉名、点对名）一律用「×」，只有方向标签用「→」，免得同一种关系出现好几种写法。
- 命名入口：边详情里的「名称」和「起点 / 终点」两行，路网页节点卡片上的「命名路口」，以及行程详情里选中某段后的铅笔按钮（后者只改单个点；选中该段时地图上的两个端点会标出起点 / 终点，反向行程的起点是段的终点）。

## 宽路口

一个 90 m 宽的十字路口在 OSM 里是十几个节点：每个方向进出各一个，四个角的人行等候区各一个，等候区宽的话每个角还能再拆。它们**不能**合并进同一个路段身份——25 m 的 `geo:` 聚类半径一放大，20–40 m 的短段就会变成自己连自己，key 失真，旧样本也没法迁移。

所以身份保持节点级，**命名单位是「路口」（`places` 表）**：

- 点任一端的「命名」，app 先提出一个草案：从该点出发，沿 ≤45 m 的段走，并把 50 m 以内的点一并纳入，最多 32 个点、距出发点不超过 150 m。对话框只显示「14 个点 · 跨度 96 m」，一个输入框，一次保存。
- **先看圈再命名**：点「命名路口」不会立刻弹框，而是把地图镜头拉到这一片（路网图通常是全城，100 m 的路口只有几个像素），用虚线圈出认领范围，提案覆盖的点加粗，下方一行「14 个点 · 跨度 96 m」加「命名这些点 / 取消」。虚线半径就是保存后用于自动归入的半径，所以圈如实表示「以后落进来的新点也会加入」。已有名字的路口也各画一个淡虚线圈，一眼能看出哪些点已经是一伙的。圈错了就取消，什么都没写。
- **大路口：「扩大范围」+ 自己点**。立交可以有 300 m 宽，而它在走过的图里和「300 m 的街道」长得一模一样：都是一串 80–130 m 的短段。没有哪个阈值能替你分辨，所以默认保持在 150 m（日常路口是对的），预览里给两种手段：
  - 「扩大范围」按 150 → 200 → 300 → 400 m 步进。`PlaceDrafts.draft(reachM)` 把段长与邻近阈值**按比例一起放大**（150 m 时正好还是 45 m / 50 m；300 m 时是 90 m / 100 m），没有第二套常数，过长的引道仍然跨不过去。
  - **直接点地图上的点挑选**：在「路网」页的预览步骤里，点任一其它路口把它加进来，再点一次移出去；加粗的点就是当前认领的，点数和跨度立刻重算。`manual` 覆盖自动规则（可以加进阈值够不到的点，也可以剔除被误吞的点），但仍不能抢已命名路口的点，seed 也不能被移走，否则就不是「编辑路口」而是解散了。
  - 镜头多留 60 m 边距，方便看清圈有没有把隔壁路口也圈进去。
- **一个路口被存成两行，按名字合并**。大 T 字路口的两个方向（直走左转 vs. 右转专用道）可以相距 70 m，默认规则够不到，于是各自被命名成同名的一行；之后不管点哪一半，另一半都被当成「别的路口」保护起来，反而把边缘的加油站吸进来——这就是「同名路口合并不了」的根因。名字是**手动写的**：在两个半边都写同一个名字，就是在说「这两半是一个路口」。所以修在写名字的这一步——`namePlace` 里 `sameNameTarget()` 发现输入的名字和附近（≤400 m）某行重名，就直接并进那一行并吸收重复行，而不是再建一行；已经存成两行时，`PlaceDrafts.draft` 也把同名近邻折进草案，`upsertPlace(absorbIds)` 在同一事务里删掉重复行。相隔超过 400 m 的同名路口不动——一座城可以有两个同名路口。`PlaceDraftTest` 用真实几何复现了这个 T + 加油站，验证合并只拿到两个转弯方向、不碰加油站。
- **有名字的点不会被顺带吸进路口**。加油站入口（单点名字）、以及和它用短段相连的出口，自动草案都不碰——加油站在水濂景观路边缘，不是路口的一部分。手动点选仍然可以把它加进来（要明确表达意图才行）。`namedKeys` 来自 `point_names`。
- 别的已命名路口覆盖的点不会被拉进来——这是唯一无法靠改名挽回的错误。
- 保存后这 14 个点共用一个名字，全部相关路段立刻改名（行程里的 leg label 同事务改写）。
- **区分小点，但不再要一份名字**：共用一个路口名后，二十个点都显示同一个名字等于没区分。所以每个点额外推一条自动副标题——**它在路口的方位 + 它所在的路名**（`PointDetails`），例如「北侧 · 人民路 × 建国路」。方位按 8 扇区（北/东北/东/…+侧），距路口中心不足 12 m 的点不给方位；路名优先取你在命名点时确认的 `point_roads`（显式优先），没确认过才退回与该点相连路段的 `user_name`（你给路段起的路名）或 OSM `name`，去重、去掉路口名本身、有几条列几条。没有专名的点也照样显示这个交叉名，不再是「未命名节点」。选点预览时这些副标题直接标在地图上，点节点后显示在卡片里；路段详情里「大路口内的小段」也补上经过它的道路，从「X 路口内」变成「X 路口内 · 建国路」。方位是现算的，路名存在点上，重新分析不会让它们过时。
- **以后新出现的点自动归入**：每次分析结束跑一遍 `adoptNewEndpoints()`，新端点要同时在路口半径内、**且离已在路口里的某个点不超过 50 m**（`PlaceDrafts.adopts()`）才会继承名字。半径说明路口有多大，不等于圈里都是它——300 m 立交的圈会把路上下一个路口也套进去，所以「认亲」按已有的点算，不按圈算。这就是 12 → 16 不再需要人工的原因，也是把范围放宽到 400 m 不会污染密集区的原因。
- 单个点的名字优先于路口名（`point_labels` 视图里 `point_names` 在前，且两者都排除含「×」的复合文本）；只想标一个角就用对话框里的「只命名这一个点」。命名时填的复合文本会被拆成 `point_roads`，不是点名。
- **以前逐点命名的点不会自动归并**：路口是 v6 才有的概念，旧的 `point_names` 保持原样，也仍然优先。给这种路口命名时，对话框会多出一行「其中 N 个点已有自己的名字」和一个开关；默认关闭（你的手写名字不会被悄悄删掉），打开后用路口名接管这些点。v7 起，旧的含「×」复合点名（以及以此命名的路口）一次性拆进 `point_roads` 并 dissolve，复合文本不再留在点名里。除此之外，这是唯一会删除单点名字的路径。
- 清空名字 = 解散路口，各点退回自己的名字或所在道路。

## 路网

「路网」标签页把路段按共享的端点连成一张图：节点是路口（`osm:` / `geo:` 身份，老数据退回坐标），边是路段。只画走过的部分，不是整城地图。

- 顶部控件按「视图 / 地图工具 / 出行方式」分开，每组各自换行；直线与沿路曲线合并成一个切换按钮，标签就是当前画法。出行方式筛选与路段页一致，只决定图里放哪些边，不改任何数据。
- 点一个节点，下方列出从这里出发的每一段：大号数字是「去」的中位耗时，小字是「回」的；点一行进入路段详情。
- 反过来，路段详情的「起点 / 终点」各有「在路网中查看」：跳回这里并预选那个节点，镜头也拉近到那一点。跳转时会清空模式筛选，免得目标节点刚好被筛掉；之后自己点节点或改筛选，镜头就恢复框住整张图。点和线在两个方向都能互查，不必合在一页。
- 副标题是节点数、边数；图分成多片时再补一个片度数。片度 > 1 说明两次出行之间还没有共享的路口，继续走就会连起来。
- 「未命名点」列出当前筛选下还没有名字、且能命名的点，按相连段数排序；已有道路名的点会显示推导出的路名，不把「没名字」误看成「没信息」。「在图上查看」只定位；「命名」沿用节点卡片的预览圈，确认范围后再保存。
- 边的方向直接来自样本的 `direction`，单行道和隔离带两侧的差异在「去 / 回」里已经分开。
- **直线 / 沿路曲线**只改地图怎么画，不改统计。默认把两端直连；切到「沿路曲线」后，优先用缓存的 OSM way 几何在两个节点之间重建中心线（`OsmPathIndex` 走最短路，异常长的路径会被拒）；两端不是 OSM 节点、瓦片没缓存或路径不连通时，退回多次未截断记录里最接近其它记录的那条（中位数形状）。两种方式都用 Douglas–Peucker 保住弯道、去掉抖动，首尾贴到节点上；都没有的段画成虚线直线，并在提示里报出段数，避免把「没数据」误看成「路本来就是直的」。两点耗时的高亮也按同样的曲线走。曲线与 OSM 索引只在切到该模式后按需加载一次并缓存；重新分析或刷新会作废旧缓存。
- 老 `mix:` 段没有可解析的端点 key，改用六位小数的坐标做身份（约 0.1 m）：同一路口通常仍能连上，但换一条轨迹经过时可能差几米而断开。
- **两点耗时**：切到「两点耗时」，在地图上先点起点、再点终点（节点卡片也有「从这里出发」）。`NetworkGraph.route()` 用 Dijkstra 找总典型耗时最低的连通路径，地图高亮这条路径，卡片给出总耗时、距离、段数和逐段明细。每段用离开当前节点那个方向的中位数；只有反方向样本时退回反向值并标明是估算，全无样本的段不能当路走。总数是各段中位数之和，不是「整趟路径的中位数」——app 没走过这整条线，不能假装有。两点的模式筛选不一致时不连通，切换筛选会清掉已选的点。

## 统计口径

`core/Stats.kt` 对每个路段、每种模式分别计算：

- **中位数**：应用展示的「典型耗时」。一条异常慢的行程不会拖偏它。
- **P25 / P75**：中间 50% 的样本落在哪。
- **截尾均值**：两端各去掉 10% 后的平均，样本 ≥ 5 时才有意义。
- **MAD**（中位数绝对偏差）：稳健的离散程度。
- **异常值计数**：落在 `[P25 − 1.5×IQR, P75 + 1.5×IQR]` 之外的样本数。
- **配速**：中位耗时 / 中位距离，换算成每公里秒数。
- **置信度**：样本 < 3 为「样本不足」；相对 IQR ≤ 0.25 且样本 ≥ 5 为「可信」；≤ 0.5 为「中等可信」；否则「参考性较低」。

方向对比同样用中位数，并给出相对合并中位数的百分比差。往返共用一条段（身份是排序后的端点对，方向是每条样本的属性），但展示上不混：两个方向都有样本时，列表和详情的大号数字直接拆成 `A → B` / `B → A` 两行，各自带中位距离和置信度——中间有隔离带的主干道，上下行本来就是两条物理道路。只有一侧有样本时，才显示合并值。样本详情页用柱状图展示全部样本，异常值以错误色标出。

另外按**时段**把样本分成四组：早上 6–10、白天 10–16、傍晚 16–20、夜间 20–6（按设备本地时区）。同一条路早上和深夜走的差别，往往比同一天两次走的差别还大；四组各给一个中位数和样本数，而不是把所有时段混成一个数字。

再按**工作日 / 休息日 × 高峰 / 非高峰**摊成一张 2×2 表（`core/TimeBuckets.kt` 的 `DayKind` / `PeakHour` / `TrafficContext`）：

- 高峰 = 07:00–09:00 与 17:00–19:00（本地时区）。早晚两次合并：判断「这趟会不会堵」看的是它在不在人潮里，不是哪一次人潮。
- 周一早八和周六早八是同一段路、同一个小时，除此之外没有一处相同，所以不合并。
- 表按行读是「周六真的更安静吗」，按列读是「高峰到底慢多少」；四行 key-value 会逼你自己在心里对齐两个轴，网格不用。
- 每个格子是中位数加样本数；空格显示「—」，不猜。
- 一次 `groupByTrafficContext()` 分桶，四组共用一遍时间戳换算。
- **周五晚高峰单列一行**（`TrafficDay` / `trafficDayOf()`）：17:00–19:00 的周五是一周里最堵的两小时，而且一年有五十二次，样本攒得比节假日快得多。它不是表里的一格，而是从「工作日高峰」里切出来的一格——高峰轴把早晚合并了，而周五只有傍晚特殊，硬塞进 3×2 会让周五早高峰去拉低「周五」的均值。切出来之后，「工作日高峰」= 周一到周四的早晚高峰加周五早高峰，含义仍然单一；单列那行给「5:31 · 4」和「比工作日高峰 +18 %」，比只报一个数有用。
- 周五如果正好是节假日或节前（2026-04-03 是清明前一天的周五、2026-06-19 是端午当天），按节假日算：出发的车流盖过「周五下班」这件事。三类的判定在 `trafficDayOf()` 里一次完成，互不重叠。
- 列表的「现在」也吃这套：周五 17:00–19:00 查的是周五那一桶，标签直接写「周五晚高峰」，样本不够时同样退回全天值并说明。

**节假日不进这张表。** `core/Holidays.kt` 内置 2024–2026 的国办节假日安排（`国办发明电`），并按日历修正工作日：

- 调休上班的周六（如 2026-02-14）按工作日算；假期里的周一、周二按休息日算——「工作日 / 休息日」读日历，不读星期几。
- 节前（假期开始前一天）和节末（假期最后一天）分别是出发和返程的车流。把它们平均进「工作日非高峰」，两头都会被污染，所以单列一张「节假日前后」，并且只有真有过这种样本时才出现。
- 2026 中秋 9/25–27 和国庆 10/1–7 之间隔着三个工作日，9/30 仍是国庆的节前——表按块算，不是按「前后相邻」算。
- 表只到 2026：更晚的日期退回普通星期规则，数据超出时界面给一行提示，而不是猜。加一年是一个 `block(...)` 加几行调休日。
- 不想等发版，就在设置页「节假日日历」里补：一段假期（`开始` / `结束`，单日只写开始），或者几个「周末上班日」。两者都存进 SharedPreferences（`custom_holidays` / `custom_workdays`），启动时按 `YYYY-MM-DD` 解析，解析失败就整条丢掉——半个日历比没有日历更糟。
- **只加不减**：自定义的假期不会取消国办的表。常见的用法是「公司多放两天」，所以相邻或重叠的块会合并成一段（`HolidayCalendar.merge`）：国庆加上 10/8、10/9 仍然只有一个节前和一个节末，节末从 10/7 移到 10/9。
- 补了 2027 的春节不等于认识 2027：`covers()` 仍然只看内置年份，提示照旧出现，只是措辞变成「除非你在设置里补过」。宁可让提示多出现一次，也不让一个空年份看起来像已覆盖。

### 等待与行进

等红灯不是「休息」，所以它不会被切出 leg；但它也不该和走路本身混成一个数字。`core/Stops.kt` 在每条 leg 内用与分段完全相同的平滑速度找出静止时段：

- 静止 **≥ 5 s** 才算一次等待，更短的只是 GPS 抖动；同一段里连续静止按一次等待计。
- 一条 leg 满足 `moving_ms + stopped_ms = end_ms − start_ms`，总耗时不变，只是多了一个拆分。
- 超过模式阈值（步行 90 s 等）的长停顿仍然是 break：两侧各自成段，那段时间不属于任何一段。
- 统计页给出「行进中位数」「等待中位数」「遇到等待的样本数」与「等待发生时的中位数」。最后一项用来区分「这段路通常绿灯」和「一旦要等就是 30 秒」。

按功能拆开来看，等待时间是**这段路成本的一部分**，但你可以单独回答「这段路本身要走多久」和「平均要在这里等多久」。

### 慢行迹象（实验）

只看 GPS，不接实时路况：同方向、非高峰且非节假日的样本取中位数作「畅通基准」；不足 3 个时退回该方向最快的四分之一，再不足就不判断。一次经过耗时达到基准的 1.3 倍，就记一次慢行，并给出这些慢行样本「多花的典型时间」。按方向分别计算，上下行不会互相当基准。

这是实验指标，不是交通事件识别：红灯、修路、下雨、走得慢都会落到同一个标志里。样本里混入的低速时段越多，基准也会被抬高，标志反而更少；效果不佳时删掉这一节和边详情里对应的卡片即可，数据库不改。

### 等红灯

只要有 OSM 路网，请求里就同时带上 `node["highway"="traffic_signals"]`。每次静止的**位置**若落在某个红绿灯节点 30 m 内，这次停顿会被另外记成「等红灯」：

- `signal_wait_ms` / `signal_stop_count` 单独存储，仍然是 `stopped_ms` 的子集，不会重复计入总时长。
- 统计页因此区分「等待」与「等红灯」：`人行横道`（`highway=crossing`）不算红绿灯；没有路网或旧缓存里没有节点的区域，只显示普通等待。
- 它仍然不知道信号相位，也分不清红灯和堵车——只是把「停在路口」和「停在别处」分开。
- 旧版本的瓦片缓存不含红绿灯节点，缓存过期后重新分析才会补上。

## 数据与隐私

- 所有数据存于应用私有目录的 SQLite（`map-of-time.db`）：行程、原始定位点、手动切段、leg、路段、本地拐点、OSM 缓存。
- 没有账号、没有云端、没有遥测。
- 设置页可把全部行程、路段、样本导出为单个 JSON，通过系统分享面板交给用户自己处理；也可以从这样的文件导入。
- 设置页最底部是红底红框的「危险区」，默认折叠，点标题栏才展开：清空单点名字、解散全部路口、清空路名、删除全部行程、清空全部数据，五项各自二次确认并先显示真实数量。单点名（`nodes.name`）与路口名（`junctions` / `junction_nodes`）互不连带，清空前两项会重写边上的缓存标签，不必等重新分析；清空路名会删掉点上的路名（`node_roads`）和边上填的路名（`edges.user_name`），边显示名不变。「清空全部数据」才连 `geo_nodes`、`nodes`、`roads`、`edges` 和 OSM 缓存一起清，设置项保留。所有这些都不可撤销，所以先导出再动手。
- 导入按「模式 + 开始时间 + 结束时间」去重，同一个文件重复导入不会翻倍；leg 用 `edgeKey + mode`（兼容旧 `segmentKey`）重新关联边，所以换机后统计仍能接上。导出格式 v4 以 `edges/nodes/roads/junctions/trips` 为一等实体；v1-v3 旧文件仍可尽量导入。
- 行程可以写备注（天气、载重、为什么这次特别慢），备注会进入导出文件。
- 忘了及时停表时，行程详情里点「修剪废点」：地图下方的时间轴箭头可以拖，也可以直接点地图上的原始定位点，两种方式同步：选中「真正到达的最后一个点」后，它之后的点会虚化半透明，确认后整段尾点和落在这段里的手动标记一起删除，然后自动重新分析，里程、点数、分段和结束时间都按留下的数据重算。只对有原始定位点且已结束的行程开放（导入的行程没有点可删，录制中的行程不能边录边删）；至少保留两个点。这一步不可撤销。
- 命名也会一起走：`points` 是单点名字，`places` 是一个路口的名字加它覆盖的点（同名路口在导入时合并成员而不是覆盖）。格式号仍是 `map-of-time/2`；旧版本读这个文件会忽略 `places`，拿到的是单点名字。

## 联网部分与使用政策

只有三处联网，且都可关闭或替换：

1. **栅格底图**（默认 OpenStreetMap，可切换为高德或自定义，见上节「底图来源」），只用于地图显示；瓦片写入磁盘缓存，离线时轨迹照常绘制。
2. **Overpass API**（默认 `https://overpass-api.de/api/interpreter`），按约 0.02°（≈2 km）瓦片一次拉取 `highway` 路网与 `traffic_signals` 节点，存进同一个数据库。
3. **GitHub Releases API**，只为应用内更新读取 `canary` 发布，不发送任何设备信息。

三者都发送可识别的 User-Agent：`map-of-time/0.1 (https://github.com/Geno1024-AIGC/map-of-time)`。Overpass 请求之间至少间隔 1 秒；单次查询 30 秒超时、连接 10 秒超时；每个行程最多请求 16 个瓦片；缓存有效期默认 120 天，可在设置页修改或清空。GitHub 匿名配额是每小时 60 次，应用按 6 小时一次的节奏自动检查，手动检查除外。

请遵守 [OSM 瓦片使用政策](https://operations.osmfoundation.org/policies/tiles/) 与 [Overpass 使用条款](https://wiki.openstreetmap.org/wiki/Overpass_API)。若要大量使用，请自建瓦片服务或 Overpass 实例，并在设置页填入自己的地址。

### 底图来源

设置页可以在三种底图之间切换。切换只影响显示，不改动任何已存储的坐标：

| 来源 | 瓦片 | 坐标 |
|---|---|---|
| OpenStreetMap | `tile.openstreetmap.org` | WGS-84 |
| 高德 | `webrd0{1-4}.is.autonavi.com` | GCJ-02 |
| 自定义 | 用户填入的模板，支持 `{z}` `{x}` `{y}` `{s}` | 可选 GCJ-02 |

- OSM 在国内时常不可达，高德是可用的替代。
- 高德瓦片按 GCJ-02 绘制，直接画原始 GPS 会偏几百米。因此绘制前会把轨迹、标记与视野中心一起做 WGS-84 → GCJ-02 偏移（`core/Gcj.kt`）；数据库里始终保存原始 WGS-84，切回 OSM 不会有累积误差。
- 高德瓦片最深只到 z=18，z=19 返回的是 179 字节的空白占位图，所以选中它时最大缩放限制为 18，避免把白图缓存下来。
- 瓦片缓存按来源分目录（`tiles-osm`、`tiles-amap`、`tiles-custom-<hash>`），换源不会串图；自定义模板改了 URL 也会换目录。
- 自定义底图默认填 OSM 模板。换成腾讯、天地图等国内服务时，记得打开「瓦片使用 GCJ-02」。

地图数据 © OpenStreetMap contributors，以 ODbL 授权；高德底图 © 高德。

### 地图打开在哪里

- 落地页（「记录」）的地图在没有轨迹时，先落到设备上一次已知的位置，再请求一次新定位替换它。之前它落在地图包的正中，那不是任何人的位置。
- 用系统 `LocationManager` 的**一次**定位（`track/Locator.kt`）：`lastKnown()` 立刻可用，`current()` 在 8 秒内等一次回调，超时就保持原样。不订阅、不常驻、不主动申请权限——权限在录制时申请，这里只是复用已经给过的那一份。
- 两分钟内的定位会被记住（`Locator.remembered()`），来回切标签不会再打一次 GPS；换城市/隔了很久则重新请求。
- 定位画成一个带光晕的点。录制中不画：那时的实时定位已经是一个标记，两个点相隔几十米会像两台设备。
- 「路网」页只在还没有任何路网可以框住时才用这个位置；有路网时仍然框住路网——那一页回答的是「我走过哪」，不是「我在哪」。
- 每张地图右上角有「锁定镜头」：数据变化（拖时间轴、新增高亮、实时定位更新）本来会重新按边界适配镜头，锁上后就不再动。锁只挡自动重适配，手动拖动和双指缩放照常可用，所以锁定后仍能把视野调到位。锁的状态只属于当前这张地图，切到别的页面会重新适配它自己的数据。

## 录制

- 使用系统 `LocationManager` 的 GPS provider，不依赖 Google Play Services。
- 前台定位服务（`foregroundServiceType="location"`）保证息屏继续采样，通知栏提供「在此切段」与「停止」。
- 所有 SQLite 写入走单线程车道；停止时先落盘最后一个点，再排队做分析，避免读到写了一半的行程。
- 进程被杀后重新启动，仍标记为「记录中」的行程会被自动分析，已采集的点不会丢。

## 整理与批量操作

- 行程列表右上角有「全部重算」；也可以点「选择」，勾选若干行程后只重算这些。重新分析会按当前算法与当前设置重切，并清理不再被引用的旧路段。
- 行程详情里可以直接改出行方式，改完自动重算：模式是路段身份的一部分，换模式意味着换一套统计口径。
- 录制时的「在此切段」（或通知栏按钮）会写入一个手动切点；重新分析时按这个时间切，适用于没有 OSM 路网、算法又漏切的路口。行程详情会把手动切点画在地图上。录完才发现漏切也可以补：行程详情点「补切点」，地图下方的时间轴箭头可以拖，也可以直接点地图上的定位点，两种方式同步；选中后确认，就按同样的时间戳记一个切点并重算——不需要重录。点错了拖动或重选即可，重复点同一个点不会记两次。行程详情的「手动切段」列出每个切点的时间，点「调整」可把切点挪到轨迹上的另一个定位点（时间轴箭头或地图点都行），点「移除」则删掉并立即重算；录制时按出来的切点也在这里改、在这里删。
- 两个时间轴两侧都有 ← →：正常走路 / 开车时一次挪一个定位点；从当前点起算平均位移速度低于 0.35 m/s（原地停留的一堆点）时，一次跳过整段静止点（最多 100 个），不必在到达后那堆废点里一格格挪。
- 路段列表支持按名称或 key 搜索，并按「样本最多 / 最近经过 / 最慢 / 名称」排序。卡片上的大号数字是**此刻**的典型耗时：按打开列表的时间落到「工作日 / 休息日 × 高峰 / 非高峰」四个桶之一（`BucketTake`）。桶里不足 3 个样本就退回全天中位数，并在下面一行写明「全部时段 · … 的样本还不够」——宁可说「还没数」，也不拿两次行程的中位数冒充结论。双向分开的路，两侧必须来自同一个桶，否则一起退回，免得一边是高峰、一边是全天。
- 每次静止都会记录发生位置，等红灯的判定就建立在这上面。
- 行程详情里地图固定在顶部，点下方任意一段，地图会缩放到这一段并高亮，其余轨迹变暗，同时地图上浮出这一段的用时、距离、等待、等红灯与方向；再点一次（或点 ✕）回到全程。分段一多也不用上下翻：地图和选中段始终在原地。

## 列表位置与导航

- 没有 NavHost：顶层只有 `tab` 与一个 `detail` 字符串（`trip:7` / `segment:12`），进详情时列表页会被整个销毁。现在 `App` 用 `rememberSaveableStateHolder()` 给每个屏幕按 key（`tab:XXX` / `detail`）存一份可保存状态，点开详情再按返回时，列表的滚动位置、筛选、排序与搜索词都原样恢复，不会跳回顶部。切换底部标签同样保留各自的位置。
- 各列表的「我在看什么」状态也一并存起来：路段页的模式筛选 / 排序 / 搜索词，行程页的多选状态，路网页的模式筛选 / 选中的路口。这样恢复的滚动位置落在的还是同一份列表，而不是被悄悄改回默认顺序的列表。`rememberSaveable` 用枚举名 / Long 列表做 Saver（`Saveables.kt`），单选状态、对话框与预览这类临时状态仍是 `remember`，不跟着保存。
- `LazyColumn` / `verticalScroll` 的状态本身就是 `rememberSaveable` 的，所以详情页内的列表、录制页和设置页的滚动也一样会被保留。

## 技术栈

- Kotlin + Jetpack Compose（Material 3），单 Activity。
- 手写 `SQLiteOpenHelper`，不引入 Room / KSP。
- 自绘 Canvas slippy map，不引入地图 SDK。
- 所有分段、路网与统计逻辑是纯 Kotlin，可在 JVM 单元测试里用合成轨迹验证（`TrackBuilder`、`OsmFixture`）。

## 构建

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:assembleDebug
./gradlew :app:assembleRelease   # 需要签名材料，见 RULES/KEYSTORE.md
```

签名从环境变量或 `local.properties` 读取（`KEYSTORE_STORE_FILE` 等），缺失时仅产出一个不能覆盖安装的包。

### CI

`.github/workflows/build.yml` 分三段，只有第二、三段能拿到签名材料：

| Job | 何时运行 | 做什么 |
|---|---|---|
| `verify` | 每次 push、PR、手动触发 | 单元测试 + `lintRelease`，上传 lint 报告 |
| `release` | 仅 `master` 的 push / 手动触发 | 落盘 keystore、`assembleRelease`（上报 build-count 服务）、用 `apksigner` 验证签名、从 APK 里读版本号 |
| `prerelease` | 同上，且带 `contents: write` | 把 APK 发布到滚动标签 `canary`（`--prerelease`） |

PR 不读任何 secret，因此 fork 的 PR 也能完整跑测试与 lint；PR 只跑 `verify`、不打包，所以不需要 build-count token。`release` 的打包会向服务上报，`pack` 取自响应。


### 版本号

`<major>.<minor>.<env>.<pack>.<sha8>`，详见 `RULES/VERSION.md`：

- `env` = `git rev-list --count HEAD`，本地与 CI 得到同一个值，是**唯一参与排序**的段。
- `pack` = build-count 服务返回的模块总数，本地与 CI 的每次打包请求都 +1（成败都算）。
- 连不上服务时（仅限网络层失败：拒绝连接、超时、DNS）打包照常进行：这一次记进 `.gradle/build-count/` 下的待补报日志，`pack` 写「已知服务总数 + 待补报数」这个预估值，构建输出打一条 warning；下一次连上服务的打包会先逐条补报，再记本次。token 错、4xx、5xx 仍然直接失败，不会伪装成离线。
- CI 不做离线兜底：runner 的磁盘随 job 销毁，留不下待补报日志，所以 `GITHUB_ACTIONS=true` 时连不上就是失败。
- `sha8` = `HEAD` 前 8 位，用于回溯。
- `versionCode = env`。
- 本地打包需要 `BUILD_COUNT_TOKEN` 与 `BUILD_COUNT_URL`：先读环境变量，读不到就读仓库根目录 `local.properties` 里的同名键（该文件已在 `.gitignore` 中）。两者都是必填——服务地址不写进仓库，否则等于把它公开给愿意刷计数的人。CI 同样从仓库 secret 读取这两项。

## 已知限制

- OSM 路口切分依赖路网数据的完整度；数据缺失时自动退回本地拐点聚类，两次经过可能落到不同身份。
- 地下、隧道、高楼之间 GPS 漂移严重，可能产生 `partial` 片段或误切；手动切段与重新分析是补救手段。
- 「典型耗时」是历史样本的统计量，不预测实时路况。
- 当前是草案阶段，数据库 schema 变更采用重建策略。
